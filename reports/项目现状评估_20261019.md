# PaperFlow 教材切题项目 —— 现状评估与不足清单

评估日期：2026-10-19
评估方式：通读 `PROJECT_HANDOFF.md`、`PAPERFLOW_AUDIT_20260813.md`、`使用说明.md`、`模型接入契约.md`、`审核协议说明.md` + 实跑测试套件 + 静态扫描 + 版本控制核查
评估范围：`F:\papercutter` 全目录（含 `desktop_annotation/`、`online_review_beta/`、`review_tools/`、`training*`、`tests/`）

## 一、总体判断

这套东西已经不是"小脚本"，而是一条**完整的生产线**：

```
教材图片 → 本地 OCR(PaddleOCR) → 版式/分栏识别 → 大题切分 → 小题切分
        → 答案页解析 → 题答配对 → 人工标注/审核 → 交付(裁图+JSONL)
        → 人工真值回流 → 训练数据导出 → 模型微调 → ONNX 契约验收 → 再上线
```

工程成熟度明显高于常见的"个人工具"水平，具体表现为：

| 维度 | 实测结论 |
| --- | --- |
| 自动化测试 | 本次实跑 `python -m unittest discover -s tests`：**408 项全部通过，62 秒** |
| 代码规模 | Python 约 30,800 行；Electron 前端 + 主进程约 19,100 行 |
| 文档 | 交接文档 918 行、审计报告 94 行、模型契约、审核协议、部署说明齐备 |
| 数据安全设计 | 原子写、`project_revision` CAS、`PROJECT_WRITE_LOCK`、路径越界校验、断点续跑完成标记、旧结果自动归档 |
| 模型工程 | 三级模型（题块/答案区/答案条目）互相隔离，ONNX 输入输出协议锁定 + SHA256 清单 + 验收脚本 |
| 线上审核中心 | PBKDF2-SHA256 20 万轮、session 只存哈希、`hmac.compare_digest`、审计事件表、按团队隔离数据 |
| 性能优化 | 有量化记录：暖缓存预标注 194.9s → 3.1s；冷页 98.1s → 50.9s |

**最难得的一点**：文档里自己写明"48/48 对应、IoU 0.996 是算法框对算法框，不能当准确率宣传"。这种清醒的自我约束在个人项目里极少见。

所以下面的问题不是"做得不好"，而是"**做得太深之后，工程基础设施没跟上**"。

## 二、必须马上处理（P0）

### P0-1　版本控制形同虚设，且一把私钥即将被提交

这是全项目**最大的单点风险**。

实测：

```
git rev-list --count HEAD   → 1        # 只有 1 个提交，2026-08-17
git status 未提交变更        → 62 项，+5277 / -1425 行
最近源码改动时间             → 2026-08-27，之后全部未入库
```

三个具体问题：

1. **产品主体根本没进版本库。** `.gitignore` 里写了 `desktop_annotation/PaperFlow-Annotation/`，而 `git ls-files | grep PaperFlow-Annotation` 返回 **0 个文件**。也就是说 19,100 行 JS 前端 + Electron 主进程 + 打包配置，**只存在于这台电脑的磁盘上**，一次误删或硬盘故障就没了，而且任何历史修改都无法回溯、无法回滚、无法多人协作。
2. **根目录躺着一把 OpenSSH 私钥。** `F:\papercutter\.paperflow-deploy-key-temp` 首行是 `-----BEGIN OPENSSH PRIVATE KEY-----`，`git status` 显示为 `?? `（未跟踪、**也未被忽略**）。下一次 `git add .` 就会把私钥提交进去。
3. **2.7 GB 训练数据没被忽略。** `runtime/training_data` 未被 `.gitignore` 覆盖，`git add .` 会尝试把整个目录塞进仓库。

附带发现：`.git` 目录占 **636 MB**，其中 5,231 个游离对象共 578 MB（最大的单个对象 73 MB）——这是历史上 `git add` 过大文件后 reset 留下的垃圾，`git gc --prune=now` 可回收绝大部分。

> 建议动作（约 30 分钟）：
> 1. `.gitignore` 追加 `.paperflow-deploy-key-temp`、`runtime/training_data/`、`*.pem`、`*key*`（按需）；
> 2. 把私钥移出工作区（挪到 `C:\Users\A001\.ssh\` 一类位置），如果它已在别处泄漏过，直接作废重签；
> 3. 把 `desktop_annotation/PaperFlow-Annotation/resources/app/`（源码部分）纳入版本控制，只排除 `node_modules/`、`*.exe`、`*.pak`、`*.dll`；
> 4. 提交一次完整快照，然后 `git gc --prune=now`。

### P0-2　精度没有可信真值，"好用"目前无法证明

`evaluate_cutter.py` 这套评估工具做得很正规（多切/漏切/合并/拆分/少裁/多裁六类指标、按整本教材划分 train/val/test），但**从来没有跑出一份基线数字**。

文档里的自我判定很诚实：

- "48/48 对应，代理均值 IoU 约 0.996" → 对比的是**已存规则框**，不是人工真值，"不能宣传为真实准确率"；
- 题块检测器在真实中文教材上"仅完成单页候选验证"；
- 答案条目检测器"尚未部署"。

后果很实际：现在没法回答老板/客户最关心的一句话——**"这套东西切 100 页，对多少页？"** 也没法判断某次改动到底是变好了还是变差了（没有回归基准，只有单元测试不挂）。

> 建议动作：抽 100 页独立人工真值（数学/语文/英语 × 单栏/双栏/三栏 × 题页/答案页），跑 `evaluate_cutter.py` 出第一份报告：框 P/R/F1、IoU@0.5、整页框数全对率、边界误差 P95。

## 三、结构性问题（P1）

### P1-3　主程序是 7,930 行的单文件，核心函数 887 行

```
cut_questions_v4.py             7,930 行 / 359 KB / 173 个函数 / 0 个类
  └─ process_book()               887 行（L6245 起）
  └─ write_paperflow_project()    340 行
  └─ process_answer_pages()       296 行
  └─ _remove_marginal_sidebar()   184 行
  └─ _split_single_col_majors()   160 行
```

里面同时塞了：CLI 参数、全局配置常量、环境变量开关、OCR 引擎管理、缓存、图像几何算法（内容掩码、页边栏剥离、页脚剥离、纠斜）、分栏检测、题号解析、答案对齐、文件输出、进度协议、运行统计。**没有任何包化分层，也没有一个类。**

`process_book` 887 行的直接后果是：改任何一个环节都要在近千行里定位，而且它承担了太多职责（跑单元、判完成、写标记、发进度、异常恢复、并发调度），单元测试很难覆盖到分支。

这已经能从测试分布看出来：7,930 行的核心切题模块，**只有 2 个测试文件 import 它**。

> 建议：按职责拆成 `config / ocr / geometry / layout / split / answer / pairing / output / cli` 九个模块，`process_book` 拆成"调度器 + 若干单步函数"。不用一次做完，先把几何算法（约 3,000 行纯函数）抽出去——它们最容易测、最值得测。

### P1-4　同一功能有三套 UI 在并行维护

| 界面 | 文件 | 行数 |
| --- | --- | --- |
| tkinter 版 | `cut_questions_gui.py` | 1,065 |
| PySide6 版 | `cut_questions_gui_qt.py` | 502 |
| Electron 版 | `resources/app/js/*` | 19,100 |

而且**两个启动入口指向两个不同产品**：

- `启动切题工具.cmd` → `launch_cutter_gui.vbs` → `cut_questions_gui.py`（Python Qt 批处理界面）
- `启动切题工具.vbs` → `desktop_annotation/.../PaperFlow人工标注工作台.exe`（Electron 标注台）

`使用说明.md` 却把 .cmd 启动的这套称为"**新版 PaperFlow 智能切题与审核平台**"——和 Electron 那套同名。用户（尤其新人）几乎必然搞混"我到底该点哪个"。

三套 UI 意味着同一个交互 bug 要修三次，而 Electron 那套还不在 git 里（见 P0-1）。

> 建议：明确"Electron = 唯一正式产品，Python Qt = 内部批处理工具"，然后在文档和桌面上把名字分开（比如 `PaperFlow 标注工作台` vs `切题批处理工具`）。

### P1-5　前后端靠 stdout 文本协议通信，很脆

`cut_questions_v4.py` 里有 **110 个 `print()`**，GUI 靠匹配 `@@PROGRESS@@{...}` 前缀解析进度：

```python
prefix = "@@PROGRESS@@"
```

隐患：任何第三方库（PaddleOCR、PaddleX）只要 print 一行到 stdout，就可能污染协议；而 stdout 里同时混着正常中文日志和 JSON。没有用结构化 IPC（socket / 命名管道 / 临时文件 + 序号），也没有 stdout/stderr 分离协议通道。

### P1-6　前端的"测试"其实是字符串匹配

`tests/test_employee_workbench_ui.py`（1,102 行，**413 处断言**）的写法是：

```python
source = (APP_JS / "main.js").read_text(encoding="utf-8")
start = source.index("async rotateCurrentPaperFlowPage()")
self.assertIn("menu-rotate-current-page", electron)
self.assertLess(method.index("await this.persistCurrentPaperFlowCache()"),
                method.index("'/api/project/rotate-page'"))
```

这只能验证"源码里某段字符串还在、顺序还没变"。它带来的是**双向误导**：

- 误报：给代码加个空格、改个变量名、重排语句，测试就红；
- 漏报：错页、竞态、渲染错位、内存泄漏——这些真正会伤到标注员的问题，一个都测不出来。

对 19,100 行、且以并发/异步为主的 Electron 前端来说，**这等于没有前端测试**。

> 建议：引入 Playwright（Electron 支持成熟）或至少 jsdom + 少量冒烟用例，覆盖：打开教材 → 翻页 3 次 → 画框 → 确认 → 重开验证恢复。5 个真跑用例的价值超过 413 条字符串断言。

### P1-7　无 CI，测试靠"记得跑"

没有 `.github/`、没有 `Jenkinsfile`、没有任何流水线配置。408 个测试目前只能靠人工执行（本次评估是我手动跑的）。加上 P0-1 的"62 项改动未提交"，实际上**没有任何机制保证提交的东西是绿的**。

## 四、文档漂移与工程卫生（P2）

### P2-8　`使用说明.md` 描述了一个已经不存在的功能

`使用说明.md` 第 20–35 行详细描述了"人员审核"的三种模式：

> **标准模式** / **实时预览**（实时切题审核台）/ **逐页审核**（每页暂停、拖框、确认后继续）

实测：`grep -rn "live_review\|逐页审核" --include=*.py` → **零结果**；`live_review_protocol.py` 与 `tests/test_live_review_protocol.py` 在 git 里都显示为已删除（`D`）。

也就是说：**说明书里最显眼的一整节功能，代码里已经不存在了。** 新员工照着点，会找不到按钮。

### P2-9　`使用说明.md` 的默认输出与代码不符

说明书写默认产出 `题目.jpg / 答案.jpg` 的目录树；而代码里：

```python
parser.add_argument('--export-crops', action='store_true',
                    help='输出裁切图片（默认：输出 PaperFlow 预标注框 JSON）')
```

**默认是输出预标注 JSON，要加 `--export-crops` 才有裁图。** 反过来，这和 `PROJECT_HANDOFF.md`"最终裁图由 PaperFlow 生成"的说法是一致的——所以是 `使用说明.md` 过期了。

### P2-10　交接文档以"窗口日志"方式膨胀，已经不可检索

`PROJECT_HANDOFF.md` 918 行，结构是"0 / 0a / 0b / 0c / 18 / 18.1 … 18.11"这种按日期和窗口追加的写法。同一件事（比如三栏修复）在 `PAPERFLOW_AUDIT_20260813.md`、`HANDOFF_三栏修复_20260819.md`、`PROJECT_HANDOFF.md` 第 11 节三处重复，内容互相覆盖，第 568 行单行长度超过 2,000 字符。

后果：想知道"当前到底是什么行为"，必须读完 918 行并自己判断哪条最新。

> 建议拆成两份：`ARCHITECTURE.md`（只写**当前**行为，随代码改）+ `CHANGELOG.md`（按日期追加，只增不改）。

### P2-11　根目录被一次性补丁脚本污染，违反自己的规范

`脚本目录说明.md` 明确要求"根目录只保留日常运行所需的核心模块"，但根目录有：

```
_apply_edits.py          5,710 B   一次性字符串替换补丁
_patch_final.py         12,700 B   同上
_patch_process_book.py  12,826 B   同上
_fix_backslashes.py      1,222 B   同上
_fix_pairs.py            1,915 B   同上
_verify_json.py          2,962 B   同上
temp_edits.py           14,856 B   同上
```

这些是历史上用"写脚本改源码"方式做大改动留下的痕迹（而且全部未提交）。它们没有任何运行价值，只会让新接手的人困惑"这个要不要跑"。

> 建议：直接删除（或归档进 `_experiments/`）。

### P2-12　换机部署仍有手工步骤

`requirements.txt` 写得很清楚，但也暴露了硬伤：

- 高精度 OCR 模型在 `C:\Users\<用户>\.paddlex\official_models\PP-OCRv6_medium_{det,rec}`，**必须从旧电脑手工复制**，不在项目目录里；
- Electron 那套 566 MB 的构建产物**没有构建脚本进版本库**，无法从源码重建，只能整目录拷贝。

这意味着"换一台电脑"目前是一次**依赖个人记忆的操作**，不是一条可重复的命令。

## 五、性能与可观测性（P2/P3）

### P2-13　冷 OCR 是体验瓶颈，缓存无上限

- 真实页无缓存结构 OCR 约 **39–51 秒**；
- 跳号重识别每处约 **13 秒**，含跳号的页整页约 **10 分钟/本**；
- `runtime/ocr_cache` 已 **17,045 个文件 / 169 MB**，进程内缓存是**无上限字典**（无 LRU、无磁盘配额、无启动预热——文档自己也列了这条债）。

### P3-14　线上审核中心的安全边界（已知债，但要写清楚）

`online_review_beta` 的鉴权实现本身是合格的（PBKDF2 20 万轮、session 哈希存库、`hmac.compare_digest`、审计表、跨团队访问拒绝）。风险在传输层和暴露面：

- **明文 HTTP**，登录口令明文传输，仅靠 ECS 安全组限公司出口 IP；一旦扩到外网/移动网络必须上 HTTPS；
- Electron `preload` 暴露较宽的通用文件 IPC（文档已列）；
- 容灾直写存在极窄 TOCTOU 窗口（文档已列）。

这三条文档都诚实记录了，属于"知道但还没到优先级"，不是隐患被掩盖。

### P3-15　异常处理与可观测性

- `except Exception: pass` 有 3 处（静默吞掉，`cut_questions_v4.py` L388、L573、L7423）；
- 110 个 `print()`，日志靠 `TeeStream` 重定向；
- **GUI 崩溃只写进 `logs/gui_startup.log`，用户界面上看不到任何提示**。历史记录里就有一个 `NameError: name 'page_index' is not defined`（2026-08-21），是靠事后翻日志才发现的——现在该处代码已重构，但这个"错误只落盘、不告知用户"的机制没变。
- 没有崩溃上报、没有指标看板（管理员进度仪表盘只是雏形）。

## 七、一句话总结

**业务闭环、数据安全设计、模型工程这三块已经达到小团队产品级水准；真正拖后腿的是"工程基础设施"——版本控制几乎没用起来、精度没有可信基线、前端测试是假的、主程序是 7,930 行单文件。**

好消息是：这些全部是**投入就能解决**的问题，不涉及重写业务逻辑。按上表 P0 两项先做，一周内项目的"可交付可信度"会有质的变化。
