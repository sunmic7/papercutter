# 甲方最终 JSON 复核 + 「生成JSON」批量管理改造（2026-11-05）

> 范围：① 管理员可删除「生成JSON」页面中已有任务并支持批量管理；
> ② 复核甲方要求的一道题目最终 JSON 到底有什么、当前程序能不能达到；
> ③ 复核 JSON 生成之后会不会乱套、有没有归属关系。
>
> 结论先行：
> - **功能已实现并部署**：管理员软删除 + 回收站 + 恢复、批量删除/恢复/取消排队/加入生成队列。
> - **甲方字段规范原件在仓库里不存在**。内部文档自己写明"枚举值必须与甲方口径一致（待确认 Q）""请甲方给词表"。因此下面字段清单是**从代码反推的实际契约**，不是甲方签字版规范。
> - **格式上能达到，数据上目前达不到**：`dataset.jsonl` 结构已实现 19 个字段，但只读试跑 54 题全部被拒收（`eligible_count=0`），仓库内所有真实 `dataset.jsonl` 均为 0 字节。
> - **归属关系分三层**：包级完整、书级/数据库完整、**单题 K12 JSON 不具备**（脱离交付包后无法反查是哪次审核、哪个版本）。
> - 发现并修掉 2 处会真正"抹掉历史"的缺陷，另补了书级版本索引；剩余 5 类风险已列清单，其中涉及**改动甲方交付契约**的留给业务决策，本轮未擅自改。

## 一、本次代码改动

### 1.1 管理员删除 + 批量管理

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 服务器 | `online_review_beta/server.py` | `submissions` 新增 `deleted_at / deleted_by_id / delete_reason`（含旧库 `ALTER TABLE` 迁移）；新增 `manage_delivery_tasks()` / `_apply_delivery_task_action()`；`POST /api/deliveries/tasks/batch`；`_submission_scope()` 新增 `scope=trash` 并让所有正常范围恒带 `deleted_at IS NULL` |
| 前端 | `online_review_beta/static/app.js` | 生成JSON 页新增「批量管理 / 回收站」开关、勾选列与全选、批量操作条、单行删除/恢复按钮、软删除原因填写、逐项结果提示 |
| 样式 | `online_review_beta/static/styles.css` | `.batch-bar`、`.check-col`、危险操作色、窄屏折行 |
| 测试 | `tests/test_review_concurrency.py` | 新增 `DeliveryTaskAdminTests` 10 项 |

**接口**：`POST /api/deliveries/tasks/batch`

```json
{ "action": "delete|restore|cancel|retry", "submission_ids": ["sub-..."], "reason": "历史测试任务" }
```

返回逐项结果，单行失败不拖垮整批：

```json
{ "ok": true, "action": "delete", "succeeded": 1, "failed": 1,
  "results": [{"id":"sub-...","ok":true,"deleted_at":"..."},
              {"id":"sub-missing","ok":false,"error":"任务不存在。"}] }
```

**权限**：`delete / restore / cancel` 仅 `admin / super_admin`；`retry` 沿用 `DELIVERY_ROLES`（审核员也可批量入队）；回收站仅管理员可见；一次上限 100 条。

**删除语义是软删除，不是物理删除**：

- 任务从任务列表、统计、生成队列、审核门禁、`scope=all` 中全部消失；
- **冻结工程 `review_previews/<id>/project.json`、逐页审核结论、审计日志、已发布的 `versions/<版本>/` 交付包全部保留**；
- 排队中/未完成的 `delivery_jobs` 自动标 `obsolete`，`running` 中的任务**拒绝删除**（避免生成到一半被摘掉）；
- 删除已审核任务后 `_ensure_book_review_approved()` 立即不再认为该书"已放行"，杜绝"任务删了却还能上传最终数据"；
- 回收站可查看删除时间与原因，一键恢复；恢复时若该书已有新的活动任务则明确拒绝，守住「一教材一活动任务」不变式。

### 1.2 顺手修掉的「会乱套」缺陷（不改甲方契约）

| # | 缺陷 | 修法 |
| --- | --- | --- |
| A | `commit_delivery_batch()` 把整个 `<教材ID>` 目录 `os.replace` 到备份后 `shutil.rmtree`，**一次旧版整包上传会抹掉 `versions/` 下全部服务器生成版本和 `current.json`** | 新增 `_carry_over_delivery_history()`：发布后把备份里的 `versions/` 与 `current.json` 回挂到新包；失败时回滚到原始目录 |
| B | `upload_delivery_file()` 允许 `relative_path` 命中 `current.json` 或 `versions/**`，可静默改写版本指针/历史文件 | 单文件接口与批次清单共用受保护路径校验（`DELIVERY_PROTECTED_NAMES/DIRS`），命中即拒绝；正常 `k12_dataset/...` 不受影响 |
| C | `current.json` 只指向最新版本，历史版本没有索引，无法从交付包反查"哪次审核" | 新增 `versions/index.json`（`paperflow-delivery-versions/v1`），每次发布追加 `version / submission_id / project_revision / snapshot_fingerprint / published_at / generated_by`，同版本重发覆盖不重复 |

`central_library.generate_delivery()` 同时增加软删除守卫：被删任务即使还有排队中的 job，也不会被取出生成、不会在生成过程中发布。

### 2.4 合格判据（决定 `eligible_count`）

`_k12_validation()`（`:200-221`）13 个错误分支 + 3 道附加门（`:332-342`）：

- 6 个元数据非空 + 知识点非空 + 题干/答案/解析非空 + 至少一张有效题图；
- 图片最短边 ≥128 px；选择题选项 ≥2；
- **题目页 `status == accepted`**、**配对关系 `status == accepted` 且有答案**、**所有答案页 `status == accepted`**；
- 只有全部满足才写入 `dataset.jsonl`，不合格题的图会被删除，原因写进 `quality_report.json`；
- 整包再有一道门：`central_library.py:581` `eligible_count < 1` 直接抛「没有符合交付规范的题目」。

| # | 缺口 | 代码/文档证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **知识点/难度/题型的封闭值域未接入交付闸** | `book_meta.py:21-49, 196-244` 定义了 STAGES/SUBJECTS/DIFFICULTY_SCHEMES，但 `delivery_workspace.py` 只 import 了 `manual_annotation_data` 和 `export_manual_annotations`，`_k12_validation` 只查非空 | 内部文档 `:165` 明确「同一批里既有 `"3"` 又有 `"中"` 是甲方最不能接受的」；当前完全不拦 |

## 三、JSON 生成后会不会乱套？有没有归属关系？

### 3.1 归属关系的三层（这是判断"乱不乱"的框架）

| 层 | 有什么 | 结论 |
| --- | --- | --- |
| **单题 K12 JSON** | 只有 `book_id`（随机 ID）、页码、页内序、印刷题号、内部 Q/A UUID | ❌ **没有** `submission_id / version / generated_at / 审核人 / 快照指纹 / batch_id`。`id` 只是包内 7 位序号，跨包不唯一。单条 JSON 脱离交付包即断链 |
| **版本包内** | `generation.json`（book_id、revision、actor_id、submission_id、version、时间）、`provenance.json`（书名、快照指纹、标注员、生成人、逐页审核人与时间、**每个文件的 sha256**）、`manifest.json`、`PaperFlow标注项目.json` | ✅ 完整 |
| **书级 / 数据库** | `current.json`（version、submission_id、revision、path、发布时间）、**本轮新增 `versions/index.json`（全量版本→审核任务索引）**、`delivery_jobs` 表、`audit_events`、`submissions/review_pages` 表 | ✅ 完整，且可追溯 |

### 3.2 已确认不会乱套的部分

- **按教材隔离**：`server.py:_delivery_root()` = `<最终交付根>/<book_id>`，正常路径两本书不会写同一目录。
- **按书加锁 + 单 worker 串行**：`central_library.py:534-536` 的 `book_locks` + `run_next_delivery_job()` 的 `BEGIN IMMEDIATE` 单条取任务。
- **版本号唯一**：`r<修订号>-<submission前8位>-<UTC时间戳>-<随机2字节>`，目录已存在直接报错不覆盖；`current.json` 只改指针，旧版本目录保留。
- **发布前竞态守卫**：生成过程中若提交被替代或删除，不发布。
- **图片与题目的关联**：题图文件名以 `sample_id` 为前缀，每题的 `image_targets` 循环内重置，只有合格题才物化，全局 `active_images` 清理孤儿图。

### 3.3 仍存在的风险（本轮已修 3 项，其余列清单）

| # | 风险 | 状态 | 说明 |
| --- | --- | --- | --- |
| 1 | 旧批次整包上传抹掉 `versions/` + `current.json` | ✅ **已修** | `_carry_over_delivery_history()` 回挂历史；有回归测试 |
| 2 | 单文件/批次上传覆盖 `current.json`、`versions/**` | ✅ **已修** | 受保护路径校验；正常 K12 路径回归通过 |
| 3 | 历史版本没有索引，`current.json` 只指最新 | ✅ **已修** | 新增 `versions/index.json` |
| 4 | **单题 JSON 无版本/审核归属** | ⚠️ 未改 | 加字段会改甲方交付契约，**需你决策**：可以规定"K12 行必须与同包 `provenance.json` 一起交付"，或在 `source` 里追加 `submission_id/version` |
| 5 | **新旧两套写入路径并存**：服务器生成写 `<book>/versions/<v>/`，旧客户端整包上传仍写 `<book>/` 本级 | ⚠️ 未改 | 本轮已让两者不再互相破坏，但同一本书仍会出现"版本包 + 本级文件"两套布局；建议后续统一收敛到 `versions/` |
| 6 | **`id` 与图片名用包内序号**，题目增删导致顺序漂移时，增量同步（`materialize_all=False`）可能复用旧题图片 | ⚠️ 未改 | 服务器流程固定 `materialize_all=True` 已规避；建议把文件名前缀改为稳定 `delivery_id`（会改交付契约） |
| 7 | 旧上传流程不写 `generation.json / provenance.json / current.json` | ⚠️ 未改 | 走旧流程的包缺少包级溯源；建议按风险 5 一并收敛 |
| 8 | 删除任务/失败批次留下孤儿文件 | ⚠️ 部分 | 本轮软删除刻意保留冻结工程与交付版本（可恢复）；`.delivery_staging/<batch_id>/`、`exports/` 失败残留仍无过期回收 |
| 9 | 两本教材复制同一份工程模板会带同一个 `delivery_book_id` | ⚠️ 未改 | 服务器导入时强制覆盖为服务器 book_id，本地独立标注流程无此保护 |

### 3.4 一句话回答你的两个问题

- **会不会乱套**：正常主流程（服务器生成、按书排队）不会互相覆盖，本轮又补上了两处会真正抹掉历史的破坏性路径；但**新旧上传流程并存**仍是最大的结构性隐患，建议尽快统一。
- **有没有归属关系**：**包级和书级有，而且本轮补强了索引；单题 JSON 本身没有**。目前反查靠"文件在哪个版本目录里"，一旦单条 JSON 被单独拷走就断链。是否给单题加 `submission_id/version`，取决于甲方是否允许扩展 `source` 段。
