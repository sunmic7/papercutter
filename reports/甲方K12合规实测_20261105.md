## 五、1000 万组迭代交付：目前不可能

甲方备注第 2 条：「第一批先采购 1000 万组，后续会增加，**增加时确保不出现重复数据**」。

| 必要条件 | 现状 |
| --- | --- |
| 全局唯一、跨批次稳定的样本 ID | ❌ `id = f"{global_order:07d}"`（`delivery_workspace.py:260`）是**包内**序号，两个包必撞 |
| 全局唯一图片名 | ❌ 文件名以包内 `id` 为前缀，跨包同名 |
| 跨批次内容指纹库 / 近似题检测 | ❌ 全仓库无 dedup / 相似度实现 |
| 重复率 ≤0.1% 的统计与报告 | ❌ 无 |
| 均衡覆盖统计（H3⑨） | ❌ 无 |

这不是「改个校验」能解决的，是**交付身份体系**缺失。但好消息是甲方「只能多不能少」，可以直接在单题里加 `submission_id / version / content_hash` 而不违约。

## 六、要达标该做什么（按优先级，均不改甲方字段契约）

**P0 — 让数据先出得来（不改交付格式）**
1. 标注入口强制填书级 `language/stage/grade/subject`、逐题 `difficulty/knowledge_points`、题干/答案/解析；
2. 题图标注与题答配对、页面 `accepted` 确认流程闭环；
3. 修前端题型默认值（`annotation-manager.js:1137` 直接赋 `'填空题'`，`main.js` / `data-manager.js` 共 6 处 `\|\| '填空题'` 兜底），否则题型错标永远静默通过；并让 `main.js:2644` 能写出 `option_image`。

**P1 — 把甲方明文词表和合规闸接进 `_k12_validation`（不改字段）**
4. `difficulty ∈ {基础,中等,困难}`、`question_type ∈ 9 个枚举`、`language ∈ {zh,en}`、`stage/grade` 值域；
5. `_write_k12_delivery` 二次复查 `illustration_candidates` 的硬拒标记；
6. PII 脱敏为小写 `x`；HTML/免责声明/广告等噪声过滤。

**P2 — 规模与身份（需要你决策，但甲方允许加字段）**
7. 全局稳定 ID（`book_id + 内容哈希` 或集中发号器）+ 跨批次指纹库 + 重复率报告；
8. 单题补 `submission_id / version / generated_at`，解决单条拷走断链；
9. H3⑥⑦⑧ 语义质量、⑨ 均衡覆盖、⑭ OCR 准确率报告，需要抽查/人工/模型评估，不能纯靠规则。
