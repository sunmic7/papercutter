## 五、五类系统性缺陷（不修还会重演）

### 缺陷 1：只有一条提交入口会冻结工程

| 入口 | 是否带 `project_document` | 结果 |
|---|---|---|
| `/api/review/submit`（标注员经桥提交） | ✅ 带 | 有冻结工程 |
| `/api/review-refresh`（审核员回传后刷新审核版本，`server.py:2442`） | ❌ 不带 | **新任务也没有冻结工程** |
| `/api/submissions`（旧提交接口，`server.py:2467`） | ❌ 不带 | 同上 |

审核员"回传修改"后走的就是 `/api/review-refresh`：它先回传工程（修订号 +1），再用快照建审核任务。此刻指纹是匹配的，**能生成一次**；但只要之后有人再保存一次工程，这条审核任务就永久报废。这就是本 case 的复现路径，只是这次连"当次匹配"都没赶上（功能上线晚于提交）。

**修复**：`/api/review-refresh` 与 `/api/submissions` 都读取服务器上的当前工程，作为 `project_document` 传入 `create_submission`。

### 缺陷 2：工程保存不会把旧审核任务标为过期

- 员工工程回传时会把旧提交标 `outdated`（`server.py:1557-1562`）
- 但**中央教材工程**保存（`operate` → `/api/project/save-cache`）只 `mirror` + 存版本，**不动 submissions**
- 结果：10 天前、内容早已不同的任务，在列表里仍显示"审核通过"，可以点生成

**修复**：中央工程保存后，若该书存在 `reviewed/in_review` 且 `project_revision != 新版本` 的提交，标 `outdated`，前端显示"需重新提交"。

### 缺陷 3：重试不预检，永久失败任务可无限重试

`retry_delivery`（`server.py:987-1000`）只检查"有没有 reviewed 提交"，不检查冻结工程是否可用。本次已经白跑 2 次。

**修复**：入队前做同样的指纹/修订号预检，不可能成功就直接 409 + 明确指引，不占队列。

### 缺陷 4：失败只说一句话，不给逐题原因

真正的"为什么 0 题合格"在 `k12_dataset/quality_report.json` 里，界面只显示一行异常文案。

**修复**：失败时把 `quality_report` 的前 N 条原因聚合进 `job.error`（或新增"查看原因"弹层）。

### 缺陷 5：审核快照只收 `accepted` 页，容易造成"全书已审"的错觉

`_page_entries`（`online_review_sync.py:52`）只挑 `status == accepted` 的页。这本书 38 页里只有 1 页 accepted，于是审核任务里只有 2 页（1 题页 + 1 答案页），全部通过后系统就认为"可生成"。

**修复**：提交审核时，若存在未确认页，明确提示"本次只提交 N/M 页"；或禁止在存在未确认页时提交整书交付。

## 六、要让它生成，必须做什么

### 路线 A：正式流程（唯一能产出甲方数据的路）

1. **补书级信息**：工作台「教材信息」填 语言 / 学段 / 年级 / 学科（可从书名猜：zh / 小学 / 六年级 / 数学）——现在是空的，54 道题全因此不合格
2. **补答案与解析**：当前 0 条答案；答案页 9 条记录只有 2 条有文本
3. **补题图**：54 道题 0 个 `illustrations`，K12 要求每题至少 1 张题图
4. **补题型/难度/知识点**：难度仅 1 条、知识点 0 条
5. **逐页确认**：37 页仍是 `unlabeled`，K12 要求题目所在页 `accepted`
6. **匹配答案**：51 道题尚未匹配答案
7. **重新提交审核** → 这一次会写入冻结工程
8. **审核员逐页放行**
9. **管理员生成** → 产出 `dataset.jsonl + images + quality_report.json`

> 只要第 1-6 步没做完，即使把冻结工程补上，生成仍会停在「没有符合交付规范的题目」。

### 路线 B：如果这条只是历史测试任务

直接作废，不必重试。重试是确定性的失败，不会因为次数增加而改变。
