# 局域网分布式总流程核查（员工本机标注 → 服务器裁剪生成）

> 触发问题：**「现在这个软件是局域网系统，员工在自己电脑上标注，最终裁剪和生成 JSON 由服务器电脑担任，这个现实情况的总流程你考虑到了吗」**
> 核查时间：2026-11-05 17:16–17:40；对象：`192.168.1.204` 生产主站 + 本机源码。
> 结论先行：**此前几轮的甲方 K12 合规实测是在本机直接跑生成器，验证的是「代码能力」，没有验证这条分布式链路。**
> 本轮做了生产服务器实测，发现 5 个断点/矛盾，其中 3 个已修并上线，2 个列为待决策。

## 三、5 个断点 / 矛盾

### 1. 【致命·已修】服务器没有把上传的原图接回冻结工程

- `review_tools/online_review_sync.py:195-221` `build_project_sync_snapshot()` 明确
  `portable.pop("book_root"/"image_root"/"answer_image_root")`，注释写「strips the local textbook locations」。
- `central_library.generate_delivery()` 用冻结工程跑
  `engine.sync_delivery_workspace()`；`manual_annotation_data.source_path()` 取
  `project["image_root"]`（空串）→ `Path("").resolve()` = 服务进程 CWD → 拼页面相对路径 → 找不到原图。
- 更早在 `build_review_snapshot()` 复现指纹时就已失败：审核指纹里含页面像素 sha256 / 宽高，也需要原图。
- `Public\SourceImages` 的原图上传功能文档（`server.py:2128-2138`）只写「给审核员本地重画框」，**从未被服务器生成链路使用**。

→ 修复：`central_library._bind_delivery_source_roots()`。按「现有绝对根覆盖页数 → `SourceImages/<book_id>`」择优绑定，
缺图时抛可操作错误（列出缺失文件名 + 「直接重试不会成功」），绑定只作用于导出副本，**冻结工程原件不改**；
`generation.json` 记录 `source_binding.mode/root/page_images`。

### 2. 【已修】旋转页 `rotated_image` 没随原图上传

`collect_project_source_images()` 只收 `page["image"]`；但 `source_path()` 在 `rotation != 0` 时读的是
`page["rotated_image"]`，审核指纹和最终裁图都用它 → 服务器必然缺这张图。
→ 修复：同一循环同时收集 `rotated_image`。

### 3. 【已修】Windows 260 字符路径上限

服务器深目录 `<root>/exports/<version>/staging/<book_id>/images/questions/P0001/<id>.jpg.tmp`
在验收环境达到 **261 字符**：目录能建（218），但打开文件失败，报裸 `FileNotFoundError`。
`numpy.ndarray.tofile()` 走 C `fopen` 更脆弱；改纯 Python IO 后仍触发 MAX_PATH，证实是路径长度而非 numpy。
→ 修复：`delivery_workspace._wide_path()` 对 ≥240 字符的 Windows 绝对路径加扩展长度前缀，
`_atomic_json` / `_atomic_image` 统一走 Python IO + 该前缀。生产路径约 233 字符暂不受影响，但更深目录/更长 ID 会触发。

### 4. 【已修】代码文案与「服务器生成」现实相反

- `build_review_snapshot()` 原 notice：「仅为审核预览；最终裁图和最终 JSON 未上传，且**必须在本地生成**。」
- `_review_submit()` 原 notice：「最终裁图和最终 JSON **仍只会在本机**由『生成裁切图片和JSON』生成。」

→ 两处改为「最终裁图和最终 JSON 由服务器在逐页审核通过后统一生成」。指纹不含 notice，改动不影响审核一致性。

### 5. 【待决策·未擅自动】两套生成入口并存

| 入口 | 位置 | 写入位置 | 门禁 |
| --- | --- | --- | --- |
| 网页「生成JSON」 | 服务器 `delivery_jobs` worker | `versions/<version>` + `current.json` | 逐页放行 + 冻结工程 + K12 校验 |
| 客户端「生成裁切图片和JSON」 | 员工本机 `_review_generate_delivery` → `upload_final_delivery` | `<book>` 本级 / 批次 | 本机指纹比对 + 上传 |

- 旧入口绕过服务器版本体系；上一轮已加保护，使旧批次上传**不能覆盖** `current.json` / `versions/**`，但两套产物仍并存。
- 客户端更新包 `20261105-server-pipeline` 的清单里**没有 `delivery_workspace.py`**，说明本机生成入口在新包里可能已不完整。
- 建议：**明确服务器生成为唯一正式路径**，把客户端本机入口降级/隐藏；因涉及 Electron 前端与全员更新包，本轮只记录、不擅自禁用。

## 七、现实总流程结论

1. **服务器承担裁剪与生成的设计确实存在**，且有 `test_full_annotation_review_delivery_cycle_preserves_originals`
   覆盖「服务器教材库」模式（原图在 `J:\原教材`，工程带服务器 `image_root`）——这条本来就是通的。
2. **但更贴合你描述的「员工本机有原书、只把标注成果和原图交给服务器」这条链路，此前是断的**：
   工程同步剥掉了原图根，服务器拿不到图，指纹复现与裁图都会失败。现已打通并实测。
3. 服务器**不需要 OCR 依赖**即可完成最终交付（裁图 + JSONL），因为 OCR 在员工电脑已完成；
   但这也意味着服务器上不能做「重新识别/补标」，需要回员工电脑处理。
4. 前面「真实 `dataset.jsonl` 全 0 字节」的主因仍是**书级元数据、题图、答案、解析、配对没填齐**
   （`quality_report.json` 里 21 题全部被 `_k12_validation` 拒收），不是这次的链路断点；
   链路断点影响的是「新版本按流程提交后能不能走到裁图」。

## 八、需要你拍板（本轮刻意没动）

1. **是否废除客户端「生成裁切图片和JSON / 上传最终交付」旧入口**，统一到网页服务器生成。
   建议：是。可一次性消除双写入路径与归属混乱。
2. **是否把 `J:\papercutter` 引擎同步纳入部署脚本**（现在是手动 scp，版本已经漂移，容易再出「改了本地没上服务器」）。
3. **服务器要不要补 OCR/预标注依赖**：若希望服务器能重做 OCR，则要装 onnxruntime / paddleocr + 模型；
   若维持「员工本机 OCR、服务器只裁图导出」，当前依赖已足够。
4. 沿用上一轮的甲方合规 P0/P1（补标注入口、修题型默认值、把甲方词表/硬拒/PII 接进交付闸）——
   这些是**数据层**问题，与本轮链路修复互不替代。
