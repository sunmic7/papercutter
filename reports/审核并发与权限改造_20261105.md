# 审核并发、冻结工程与生成 JSON 权限改造（2026-11-05）

## 0. 触发与目标

用户反馈："这个 json 不能生成或者生成失败"，且明确说明这是**历史测试任务**，软件仍在测试阶段；
随后要求：

> "现在需要你全面改相关代码，以后多人同时提交，反复提交，管理员重试，审核员修改等等行为都不要出错，
> 另外审核员也应该具有'生成 json'这个菜单中的所有权限。"

只读排查结论见 `reports/JSON生成失败排查_20261105.md`：不是生成器坏了，而是
**历史任务没有冻结工程 + 工程已改 + 0 道 K12 合格题**，重试是确定性失败。
排查同时暴露 5 个系统性缺陷：提交入口不冻结工程、工程保存不退役旧任务、
重试不预检、失败原因不可操作、审核快照只收 `accepted` 页。

本次改造目标是让这些行为在**任何并发、重复、重试、回传组合**下都不出错。

## 1. 设计：一教材一活动审核任务

| 概念 | 取值 / 位置 | 作用 |
| --- | --- | --- |
| `ACTIVE_SUBMISSION_STATUSES` | `pending / assigned / in_review / reviewed / returned / needs_fix` | 定义"活动任务"全集，任何入口都按它收敛 |
| `DELIVERY_ROLES = REVIEW_ROLES` | `super_admin / admin / reviewer` | 审核员拥有「生成 JSON」菜单全部动作 |
| `UNFINISHED_JOB_STATUSES` | `queued / running` | 旧版本生成任务要被取消 |
| `delivery_jobs.status` 新增 | `obsolete` | "该审核版本已被新提交替代，生成任务已自动取消。" |

唯一的收敛点：`_supersede_active_submissions(connection, book_id, keep_id, reason, actor_id)`。
在 `BEGIN IMMEDIATE` 事务里把同书其它活动任务标 `resubmitted` / `outdated`，
并把它们未完成的 `delivery_jobs` 标 `obsolete`，写审计事件。
所有提交入口（`/api/submissions`、`/api/review-refresh`、`/api/projects/sync` 带 `review_snapshot`
、中央库 `/api/review/submit`、`/api/review/push-project`）都汇流到 `_create_submission_record()`。

**冻结工程**：每次创建任务都强制写 `review_previews/<submission_id>/project.json`。
`_create_submission_record()` 依次尝试 `project_document` 参数 → 快照内嵌 `project_document`
→ 服务器已存工程 `_project_for_freeze()`；三者皆无则直接拒绝：
"缺少审核冻结工程，服务器无法保证审核内容可复现，请重新打开服务器工程后提交。"
并校验冻结工程 `project_revision` 与审核版本一致。以后不再存在"能提交但永远生成不了"的任务。

**工程被编辑**：`note_project_saved(db, book_id, revision, actor_id)` 在中央工程保存事务里
把修订号不匹配的活动任务标 `outdated`、未完成队列标 `obsolete`（已成功发布的任务保留在历史里）。

**生成前预检**：`delivery_preflight(submission_id)` 检查任务仍 `reviewed`、无未通过页、
冻结工程存在且修订号一致。`retry_delivery()` 入队前调用，永久性损坏的历史任务在队列门口
就被拒，不再让管理员无限重试；文案明确写「请重新提交并逐页审核新版本（直接重试不会成功）」。

**发布前最后防线**：`generate_delivery()` 在写 `current.json` 前重新查库，若该任务已不是
`reviewed` 就抛错不发布，避免生成过程中被新提交抢跑。

**幂等**：
- `create_submission(..., idempotent=True)`：按 `(book_id, project_revision, snapshot_fingerprint, 活动状态)`
  命中就返回原任务并顺手清理散落的活动任务。
- `_reviewer_repeat_result()`：审核员回传的第一个请求把工程版本从 `N` 推到 `N+1` 并创建任务；
  响应丢失后客户端用同一个 `base_revision=N` 重放，服务器识别
  `(stored=N+1, fingerprint, live task)` 直接返回原结果，而不是 409 把操作员卡死。

**审核员回传原子化**：`push_project_snapshot(..., review_snapshot=...)` 把工程修改与审核快照
放进同一个 `/api/projects/sync` 请求；服务端在一个事务里写工程、退役旧任务、写冻结工程、
创建新任务。新服务器直接返回 `submission`，不再单独打 `/api/review-refresh`；
老服务器兼容路径仍会补发带 `project_document` 的 refresh 请求。

## 4. 部署：一次失败与修复

**第一次部署**：文件上传完成，但远端健康检查 20 秒超时，本机访问 `.204:8787` 也是 HTTP 000。
远端诊断结论：

```
Execute        : C:\windows\System32\WindowsPowerShell\v1.0\powershell.exe
Arguments      : /d /c "J:\PaperFlowData\System\run-review.cmd"
LastTaskResult : 1
IMPORT_OK / PROD_STORE_OK / SUBMISSIONS 2 / ALIVE_AFTER_6S True
```

即代码可导入、生产库可初始化、手动启动可运行，问题**只在计划任务动作配置漂移**：
`Execute` 被改成 `powershell.exe` 但参数仍是 cmd 的 `/d /c`，启动即返回 1。
修复方式是在部署脚本里每次强制写回 `cmd.exe` 动作，第二次部署 7 秒完成，
远端与本机健康检查都返回 `{"ok":true,"service":"paperflow-review-beta","schema_version":1}`。

**教训（已写入部署脚本注释）**：不要用手工改过的计划任务动作当基线；部署脚本必须自愈动作配置。

## 7. 边界与后续注意

1. **子仓库 `online_review_beta/` 的 push 会触发 ECS 云端站自动更新**。
   本次只在本地 commit，**未 push**，是否推送由用户决定。主站 `.204` 已部署且不依赖 GitHub。
2. 工作区里 `server.py` / `app.js` / `paperflow_annotation_api.py` 等文件同时含有
   10-21 之后其他 AI 的未提交改动。本次提交的是**已通过 855 项单测 + 17 项真机验收的工作区完整状态**；
   部署脚本与更新包也使用同一份，不存在只推半成品的情况。
3. `question_detector.onnx` 按用户指示**未动**。
4. 审核快照 `build_review_snapshot()` 只收 `accepted` 页这一条**本次未改**（属于标注口径问题，
   不是生成链路 bug）；若要避免"38 页只审 2 页却显示全部通过"，需单独决策。
5. K12 交付本身的 `eligible_count` 仍取决于书级字段与逐题答案/解析/题图是否齐全，
   这是数据质量门禁，不是代码缺陷。
