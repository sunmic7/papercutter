# 服务器相关操作全面提速（2026-11-06）

按"能不能更快、会不会卡住"逐条审计了所有与服务器打交道的路径：保存到服务器、提交审核、
原图上传、审核站网页、教材库扫描、生成交付。下面是每一条的耗时构成、改动和实测结果。

## 一、结论表

| # | 路径 | 原来 | 现在 | 依据 |
|---|---|---|---|---|
| 1 | 保存到服务器（员工） | 生成交付/样例题库期间全程排队，最长等到分钟级 | 只排真正的同书写入，其余并行 | `generation_locks` / `ready_locks` 与 `book_locks` 分离 |
| 2 | 保存时 JSON 序列化 | 在全局锁里 `json.dumps` 整本工程 | 锁外序列化 | server.py `sync_project_snapshot` |
| 3 | 提交审核（快照构建） | 串行 117 ms/页，51 页约 **6.0 s** | 冷 **1.50 s**、热 **0.14 s** | 并行 + 预览缓存 + 每页只读一次文件 |
| 4 | 提交审核（请求体） | 整本 base64 内联 JSON，51 页 **11.6 MB**（150 页约 34 MB，还会撞 128 MB 上限） | JSON **26 KB** + 预览按哈希二进制上传 | `page-previews` 中转区 |

## 二、保存到服务器

### 之前为什么慢

两条独立的锁链叠在一起：

1. `_sync_ready_samples()`（实时样例题库）**全程持有书级锁**，裁图要几十秒；员工一保存就排队。
2. `generate_delivery()` 也吃同一把书级锁。生成交付要几十秒到几分钟，这期间同一本书的保存全部堵死。
3. `sync_project_snapshot` 在**全局锁里**做 `json.dumps(整本工程)`，一本 1 MB 以上的工程会顺带卡住所有其他请求（含心跳、审核结论）。

### 改法

- 书级锁 `book_locks` 只保护"读工程文件 + 写工程文件"这一小段。
- 实时样例题库改用独立的 `ready_locks[book_id]`：重算只在重算之间排队。
- 生成交付改用独立的 `generation_locks[book_id]`：保证同一本书不会同时生成两个版本，但**不阻塞保存**。
- 工程 JSON 在进锁之前就序列化好（审核员回传要改 `project_revision`，那条路仍在锁内序列化）。
- 加慢日志：等锁超过 1500 ms 就往 stderr 打一行 `[book-lock] <book> 等待书级锁 N ms（操作）`。以后再觉得慢，看日志就能定位是谁占着。

### 效果

保存不再受裁图/生成影响。同一本书**同时**点"生成交付"和"保存"时，保存会立刻返回，生成在后台跑完。

## 三、提交审核

### 3.1 客户端生成预览：6.0 s → 1.50 s（冷）/ 0.14 s（热）

原实现三个问题：

1. 每页把整张扫描读**两遍**（一遍算 SHA-256、一遍给 OpenCV 解码），1.8 MB/页。
2. 串行解码 + 缩放 + 编码，实测 117 ms/页。
3. 每次提交都重算，哪怕这一页上次已经算过。

现在：

- 每页只 `read_bytes()` 一次，指纹和解码共用同一份字节。
- 预览按 `SHA256(原图) + 边长` 缓存在 `%LOCALAPPDATA%\PaperFlow\preview-cache`，内容没变的页直接命中。
- 多线程并行（默认 `min(6, CPU)`，可用 `PAPERFLOW_PREVIEW_THREADS` 覆盖）。

实测（51 页真实扫描，`_experiments/bench_submit_preview.py`）：

```
冷启动(空缓存)      1.50s    29 ms/页   51 页   预览二进制 8.7 MB   JSON(不含预览) 26 KB
再次提交(命中缓存)  0.14s     3 ms/页
第三次              0.14s     3 ms/页
老算法串行：117 ms/页（实测 24 页均值），51 页约 6.0 s
```

缓存有上限（6000 张，超出按最久未用淘汰），不会把员工机器撑爆。

### 3.2 请求体：11.6 MB → 26 KB + 二进制

原来整本预览 base64 塞进一个 JSON：51 页 8.7 MB 预览 → **11.6 MB** 请求体。一本 150 页的书约 34 MB，
既慢又逼近 `MAX_BODY_BYTES = 128 MB` 的硬上限（超大对开页扫描会直接提交失败）。

现在分两步：

1. `GET /api/projects/<book_id>/page-previews` 拿服务器已有的预览哈希列表。
2. 只把缺的几张用 `POST /api/projects/<book_id>/page-previews` 以**原始 JPEG** 传上去（带 `X-Paperflow-Sha256` 头，服务端按内容哈希落盘、重复内容只存一份）。
3. 提交 JSON 里只留 `{page_key: sha256}`，26 KB。

同内容重提时第 2 步一张都不用传。

### 3.3 兼容

- 老客户端（内联 base64）照旧能提交：`_page_preview_bytes` 优先读内联，没有再去中转区找。
- 新客户端遇到老服务器：`stage_submission_previews` 探测接口失败 → 自动退回内联 base64，不会提交不了。
- 请求体 gzip：大于 256 KB 才压；服务端不认 `Content-Encoding: gzip`（老版本）时自动明文重发一次。

## 四、原书页上传

`upload_project_source_images` 原来是"一张一张 base64 POST"。一本 150 页的书 = 150 个来回，
每张还因为 base64 多 33% 体积（1.8 MB → 2.4 MB）。

现在：原始二进制 + `X-Paperflow-Sha256` + 4 连接并行，上传在**工作线程里读文件**
（避免 200 张 × 3 MB 一次性读进内存把工作站拖死）。老服务器失败时自动退回原来的 base64 路径。

## 五、审核站网页

| 改动 | 原因 |
|---|---|
| `protocol_version = "HTTP/1.1"` | 一屏几十张缩略图，每个请求重新 TCP 握手明显发涩 |
| `ReviewHTTPServer.request_queue_size = 128` | 默认 backlog 只有 5，多开页签就打满队列、浏览器报"连接被重置" |
| 空闲连接 30 s 回收 | 长连接会把线程挂着，太多会占满线程 |
| 静态图片/预览带 `ETag` + `max-age` | 原来 `no-store`，审核员来回翻页每次都重下整张扫描；现在第二遍是 304 |
| JSON 响应 gzip | 任务列表、教材库、工程快照动辄几百 KB，压缩后省 70%+ |
| `BrokenPipeError` 静默处理 | 翻页太快掐掉上一张时，不要往已发出的响应里再写 JSON |

预览图 URL 里带 `submission_id`，内容不可变，缓存是安全的。

## 六、教材库扫描：16.3 s → 1.0 s

`_discover_books` 原来**两遍**文件系统：

1. `os.walk` 找含图片的目录；
2. 对每本候选书 `rglob('*')` 再走一遍，而且**对每个文件**都调 `resolve()`（每个路径组件都要问一次文件系统）。

改成一遍 `os.scandir` 递归，统计信息直接取 `scandir` 的缓存属性；汇总时用规范化字符串前缀比较，
不再对"候选书 × 含图目录"做 `Path.is_relative_to`。

实测（`_experiments/bench_library_scan.py`，`F:\11教材\2017`，114 本）：

```
新实现   1.38s / 1.03s
老实现  16.31s / 17.02s
提速 16.56x    老有新无 0  新有老无 0  计数/体积不一致 0
```

结果完全一致（含"题目/答案/1/"这类子目录的计数与体积）。

## 七、实时样例题库

原来只比 `project_revision`，而工作台每保存一次就 +1（切页也算），于是整本重裁在员工填题的
十几分钟里反复重跑。现在比**内容指纹**（`content_fingerprint`，只覆盖审核看到的字段），
内容一样直接跳过并把修订号追平。

## 十、还剩什么

1. **客户端要重新发包才生效**：预览并行/缓存、二进制上传、gzip 都在 `review_tools/online_review_sync.py`（工作台本机进程）。服务器端改动已经在线上，老客户端能用但拿不到这波提速。
2. **生成交付期间**同一本书仍会短暂互斥（`generation_locks`）——这是必要的，两个版本不能同时生成。
3. **中转区容量**：每本书最多留 400 张预览，全局最多挂 80 本书（`STAGED_PREVIEW_KEEP` / `STAGED_PREVIEW_BOOKS_KEEP`，淘汰最久未用），超出自动清理。
